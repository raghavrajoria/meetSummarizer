meetReaderCB — deployment notes for infra
=========================================

WHAT THIS IS
------------
A purely static site. No backend, no database, no build step, no environment
variables, no API keys. Unzip and serve the folder.

  Entry point : index.html   (sign-in screen)
  Routes      : index.html -> dashboard.html -> meetings.html -> meeting.html
                plain files, no rewrite rules needed

Total size ~55 MB, almost all of it the two videos under media/.


REQUIREMENTS
------------
1. HTTP RANGE REQUESTS MUST WORK.  <-- the one thing that will break it

   The page uses a custom HTML5 player. Without `Accept-Ranges: bytes` and
   206 responses, the browser reports the media as non-seekable, the scrub bar
   will not move and clicking a transcript timestamp will do nothing.

   nginx, Apache, IIS, S3/CloudFront, Netlify, Vercel and GitHub Pages all
   support this out of the box. The usual cause of breakage is a reverse proxy
   or CDN rule that buffers or rewrites responses and drops Range. If you put
   anything in front of the origin, confirm Range survives it.

   Verify:
     curl -s -D- -o /dev/null -H "Range: bytes=0-99" https://HOST/media/demoexample1.mp4
   Expect: HTTP/1.1 206 Partial Content
           Content-Range: bytes 0-99/14217831
           Accept-Ranges: bytes

2. CORRECT MIME TYPES
     .mp4  -> video/mp4
     .css  -> text/css
     .js   -> application/javascript
     .html -> text/html; charset=utf-8

   The transcripts are Bengali, Hindi and English. Serve HTML, CSS and JS as
   UTF-8 or the Indic text will render as mojibake. The files are UTF-8 and the
   HTML declares <meta charset="UTF-8">, but a server that forces a different
   charset in the Content-Type header will override that.

3. HTTPS RECOMMENDED
   The Copy buttons use navigator.clipboard, which browsers only expose on a
   secure context (https, or localhost). Over plain http the code falls back to
   document.execCommand("copy"), which still works in current browsers but is
   deprecated. Everything else is unaffected.


SUGGESTED HEADERS
-----------------
  /media/*        Cache-Control: public, max-age=31536000, immutable
  /css/*, /js/*   Cache-Control: public, max-age=3600
  *.html          Cache-Control: no-cache

Media is large and never changes; HTML should not be cached hard while the demo
is being iterated on.


ACCESS CONTROL — PLEASE READ
----------------------------
The recordings in media/ are real meetings featuring identifiable people who
did not consent to publication. demoexample1 in particular is an internal
review call in which named employees are reprimanded.

This should NOT be on a public, indexable URL. Put it behind one of:
  - HTTP basic auth, or
  - an IP allowlist, or
  - an unguessable hostname plus  X-Robots-Tag: noindex  and a robots.txt
    disallow

That is a decision for whoever owns this, not a technical blocker — but it
should be a deliberate choice rather than an oversight.


SMOKE TEST AFTER DEPLOY
-----------------------
  1. GET /              -> sign-in screen, wordmark reads "meetReaderCB"
  2. Sign In (any input) -> Overview, four stats populated, one meeting listed
  3. "All dates"         -> two meetings, Speakers becomes 11, time 16m 34s
  4. Open a meeting      -> video frame paints, duration shows (8m 33s / 8m 1s)
  5. Press play          -> audio plays, scrub bar advances
  6. Drag the scrub bar  -> position changes        <- fails if Range is broken
  7. Transcript tab      -> Bengali/Hindi text plus English beneath it
  8. Click a timestamp   -> recording jumps there, that line highlights
  9. Download transcript -> .txt downloads, Indic text intact when opened

If 6 fails, it is Range. If 7 shows boxes or garbled characters, it is charset.


NOT FOR PRODUCTION USE
----------------------
  - serve.py is a local development server only. Do not run it as the
    production origin. It is included so the team can preview locally.
  - Sign-in is a mock: the form does not authenticate, it just navigates to
    dashboard.html. There is no session, no user store, no authorisation.
    Anyone who reaches the URL sees everything. This is why the access control
    note above matters.
  - Summary "Edit" changes are in-memory only and vanish on reload.
